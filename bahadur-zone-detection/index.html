Automatic Zone Detection for Bahadur

This manual explains the task handover of 19 October 2026. It tells you what the problem is, what you must learn, and how to do the work. The text uses Simplified Technical English: short sentences, active voice, and one instruction in each step.

The target result
Make a zone for the front porch and one for the driveway.
camera: front_door

2 zones proposed: porch_approach and driveway. The preview is ready. Bahadur saves nothing until you approve each zone.

Source: Task handover, @Chirag Duration: 5 weeks Product: Bahadur NVR
NOTE

The PDF header says “RFP: Automatic Zone Detection for Frigate”. Bahadur uses the same configuration keys as the open-source Frigate NVR. Thus, you can use the Frigate documentation to learn Bahadur. Confirm the exact Bahadur version in week 1.

01

Summary

Bahadur is a network video recorder (NVR). It finds people, cars and other objects in camera video. A zone is an area of the camera image that the user marks as important. Today, the user draws each zone by hand. Your task is to make Bahadur propose the zones automatically.

The feature has three parts:

  • Tools. Functions that an LLM can call to get current and past frames from a camera.
  • Analysis. A heat map that shows where objects move, and a vision model that names the areas in the frame.
  • Zone drawing. A step that combines the analysis with the user's request and writes valid zones.
Input
One sentence from the user, for one camera.
Output
Named zone polygons that are ready for config.yml.
Speed
Less than one minute for each camera.
Approval
The user previews each zone. Bahadur saves nothing without approval.
Models
A local vision model by default. Cloud APIs are optional.
User
A home or small-business operator with no computer-vision knowledge.
Fit
Use Bahadur's config and UI. Do not replace them.
Plan
5 weeks, 4 workstreams, 9 deliverables.
02

The problem

Zones control the behavior that users care about most. They decide which objects make an alert, which filters apply, and which automations start through MQTT and Home Assistant. Users draw zones by hand. This causes three problems.

The work also repeats. An operator with many cameras makes the same decisions on each camera: the driveway is here, the public sidewalk is there, the door is up there.

Today
  1. Open Settings → Masks / Zones.
  2. Click each corner of the polygon.
  3. Guess how large the zone must be.
  4. Do steps 1 to 3 again for each camera.
  5. Draw the zone again when the camera moves.

Result: hours of work, and zones that are often wrong.

Target
  1. Type one sentence for the camera.
  2. Examine the proposed zones on the frame.
  3. Accept, edit or reject each zone.

Result: zones that the user would draw, in less than one minute, without leaving Bahadur.

Bahadur already has the raw material for this feature:

  • A motion detector.
  • Object tracking, with bounding boxes and history in its database.
  • A latest.jpg endpoint for each camera.
  • Event snapshots.
  • A config API.

Community MCP servers already connect LLM assistants to Bahadur. They prove that the tool-call method works. The missing part is the pipeline that turns frames and history into proposed zones. You will build that pipeline.

03

How a zone works

Learn this rule first. Bahadur does not test the full object box against a zone. It tests one point: the bottom-center of the box.

This rule has two results for your work:

  • A zone must cover the ground where feet and wheels touch. It must not cover only the body of the object.
  • The heat map must use the same bottom-center points. Then the heat map and the zone test agree.

Zones live in config.yml, under each camera. This example is the result of the prompt at the top of this manual:

cameras:
  front_door:
    zones:
      porch_approach:
        coordinates: 0.613,0.506,0.669,0.506,0.734,0.833,0.938,0.833,1.000,0.961,1.000,1.000,0.484,1.000,0.516,0.833,0.641,0.833
        objects:
          - person
        inertia: 3
        loitering_time: 0
      driveway:
        coordinates: 0.086,0.506,0.297,0.506,0.409,1.000,0.000,1.000,0.000,0.728
        objects:
          - person
          - car
    review:
      alerts:
        required_zones:
          - porch_approach
      detections:
        required_zones:
          - driveway
KeyWhat it doesIn the example
coordinatesPolygon corners as x,y pairs. Values go from 0 to 1, relative to the frame.9 corners
objectsOnly these labels can trigger the zone.person
inertiaNumber of frames that an object must be in the zone before it counts. This stops false entries.3
loitering_timeSeconds that an object must stay in the zone before it counts. The value 0 turns it off.0

The four workstreams

WS1Frame and history tools

Week 1D2

Give an LLM small, safe tools to read Bahadur cameras. This is a thin wrapper over Bahadur's HTTP API, as an MCP server plus a Python client. It takes days, not weeks.

ToolIt returns

get_latest_frame(camera, options)The current frame. Optional overlays: boxes, zones, motion boxes. Optional downscale.
get_frames(camera, start, end, count, filter)A sample of past frames or event snapshots, so the model sees day, night and activity. Filter by object label.
get_object_history(camera, start, end, labels)Positions of tracked objects over time: bottom-center points and boxes. This is the raw input for the heat map.

  • Authenticate against Bahadur's API. Obey its auth model.
  • Return compact, structured results that fit in an LLM context.
  • Do not block Bahadur's detection loop.

Done when An LLM client can list cameras, get a frame and get object history through the MCP server.

WS2Heat map

Week 1D3

Make a map of where objects actually move, for each camera.

  1. Get the bottom-center points of tracked objects for a time window. The default window is 7 days.
  2. Add each point to a grid at detect-stream resolution. Weight each point by label and dwell time.
  3. Keep one map for each label class: person, car, dog, package. You can also keep one map for each time of day.
  4. Smooth the grid. Find the connected high-activity areas: blobs, paths (entry and exit routes) and dwell hotspots.
  5. Change each area into a simplified polygon with a confidence score.
  6. Render the map as an image overlay. The LLM and the user both see this image.
NOTE

Parked cars and other stationary objects stay in one place for hours. Dwell weight then makes them the hottest spot on the map. Set a maximum dwell weight for each tracked object.

Done when The CLI renders a heat map overlay for a camera from its object history.

WS3Scene understanding

Week 2D4

Name the areas in the frame and give each area a precise outline. Use models that already exist. Do not train or fine-tune a model.

drivewaysidewalkroadlawnporchdoorgatepoolfence lineparked vehiclesneighbor property
  1. Use a vision-language model (VLM) to name the regions.
  2. Use a segmentation model (SAM or similar) to get the exact polygon of each region.
  3. Return each region with a label and a confidence. Also return the apparent field of view and horizon of the camera.
  4. Use a local open-weight model by default. Support cloud vision APIs through the same interface.
CAUTION

Night and infrared frames have little color and detail. If the confidence is low, report it. Do not guess.

WS4Intent-driven zone drawing

Weeks 3–4D5 · D6

Turn the user's sentence into correct zones. This is the orchestration layer. It calls the tools, reads the analysis and writes the zones.

  1. Parse the prompt into structured goals: areas to watch or ignore, object types, alert or detection, loitering.
  2. Combine heat-map regions and semantic regions according to the goals. Example: “watch the porch” means the porch region plus the approach path that the heat map shows.
  3. Make valid zones. See the rules below.
  4. Show the zones as an overlay in the Bahadur UI. Let the user accept, edit or reject each zone.
  5. Apply the accepted zones through Bahadur's existing save path and restart handling.
  6. Accept follow-up prompts, for example “make the driveway zone stop at the sidewalk”.

Rules for a valid zone

  • A simplified polygon with 12 or fewer vertices.
  • All points inside the frame.
  • No self-intersection.
  • A clear name, for example porch_approach.
  • Suggested values for the objects filter, inertia and loitering_time.
  • A rationale in plain language for each zone.

Out of scope

  • Motion masks. This can be follow-on work.
  • Changes to Bahadur's detector, tracker or recording pipeline.
  • Hosting of cloud LLM services, or payment for them.

Done when A user types one sentence, examines the proposal, approves it, and the zones work.

06

Safety rules

CAUTION

Do not write to config.yml before the user approves. A wrong zone can stop real alerts, for example an alert for a person at the door.

  • Stage each change as a patch. Validate the patch before you save it.
  • Use Bahadur's existing save path. Do not write the YAML file directly.
  • Keep frames on the local machine by default. Send frames to a cloud API only when the user enables it.
  • Do not run heavy work inside the detection process.

09

Recommended approach

Let the model choose.
Let geometry draw.

Vision-language models name things well. They place exact coordinates badly, and they give different coordinates on each run. A zone is exact geometry. Thus, do not ask the model for coordinates. First, measure the regions with code. Then ask the model to choose and combine the regions by number.

Day 1–3

Make the test set first

You need a number to compare models and to show progress at each weekly demo. D4 requires this set anyway.

DOCollect 20 or more frames from 4 or more scene types: front door, driveway, backyard with pool, shop entrance, night IR. Draw the correct zones by hand. Write two prompts for each frame. Score each run with IoU, the validity rules and the time.

Week 1

Build a walking skeleton

A thin end-to-end path finds integration problems early. After that, each week makes one part better.

DOConnect prompt → heat-map region → valid polygon → staged patch → preview image. Use no VLM yet. Then replace one simple part with a better part each week.

Week 2

Make a clean plate

The camera does not move, so the scene geometry is the same in all frames. Parked cars, people and shadows hide parts of the scene.

DOTake the per-pixel median of about 30 daylight frames from different hours. Segment this clean plate one time. Use its polygons for night and IR frames too. Use night frames only to check that the camera did not move.

Week 2

Number the regions

A model refers to a number much more reliably than to a pixel position. This is the Set-of-Mark method.

DODraw each segmented region and heat region with a large number on the frame. Send the marked image and a compact table: id, label, confidence, area, heat share for each label, neighbors.

Week 3

Write a zone program, not coordinates

A program is repeatable and testable. A follow-up prompt can edit it with one more step.

DOLet the LLM return JSON operations: take, union, subtract, grow_along_heat, buffer. Validate the JSON with a Pydantic schema. Run it in a geometry engine that always obeys the zone rules.

Week 3

Let heat shape, let semantics name

Segmentation knows what an area is. The heat map knows where objects really go. One alone is not sufficient.

DOStart from the semantic region. Grow it into connected heat cells. Stop at the regions that the user wants to ignore. If segmentation confidence is low, use the heat region and tell the user.

Week 4

Cache the scene for speed

The time limit is one minute. Segmentation and heat maps are slow, but they do not depend on the prompt.

DOCompute the clean plate, the regions and the heat maps in the background, for example each night or when the user adds a camera. A prompt then needs only one LLM call and fast geometry.

All weeks

Use fake cameras for tests

Real cameras give different results each day. Tests must give the same result each time.

DOLoop recorded video files as camera inputs in a Bahadur Docker container. Let Bahadur build object history from them. Use this container for the D7 integration tests.

The zone program

For the prompt at the top of this manual, the LLM returns this program. It uses the region numbers from Figure 4D.

{
  "zones": [
    {
      "name": "porch_approach",
      "steps": [
        {"op": "take", "regions": [5, 4]},
        {"op": "grow_along_heat", "label": "person", "max_px": 40},
        {"op": "subtract", "regions": [1, 2]}
      ],
      "objects": ["person"], "review": "alert", "inertia": 3, "loitering_time": 0,
      "rationale": "The porch, plus the walkway that people use to reach it."
    },
    {
      "name": "driveway",
      "steps": [
        {"op": "take", "regions": [3]},
        {"op": "grow_along_heat", "label": "car", "max_px": 30}
      ],
      "objects": ["person", "car"], "review": "detection",
      "rationale": "The area where cars park and people walk to the house."
    }
  ]
}

A follow-up prompt adds one step. For “make the driveway zone stop at the sidewalk”, the LLM returns:

{"zone": "driveway", "append": {"op": "subtract", "regions": [2]}}

The geometry engine runs the steps. It then makes sure that each zone obeys the rules:

def run_program(program, regions, heat, frame_box):
    for zone in program.zones:
        shape = Polygon()
        for step in zone.steps:
            shape = OPS[step.op](shape, step, regions, heat)
        shape = largest_part(make_valid(shape).intersection(frame_box))
        shape = simplify_to(shape, max_vertices=12)
        assert shape.is_valid and vertex_count(shape) <= 12
        yield to_bahadur_zone(zone, shape)   # normalized 0–1 coordinates

def simplify_to(shape, max_vertices):
    lo, hi = 0.0, 50.0                       # tolerance in pixels
    for _ in range(20):                     # binary search
        mid = (lo + hi) / 2
        if vertex_count(shape.simplify(mid)) <= max_vertices:
            hi = mid
        else:
            lo = mid
    return shape.simplify(hi)

Glossary

NVR
Network video recorder. Software that records and analyzes camera video.
Zone
A named polygon on the camera image. Bahadur uses it to filter alerts and detections.
Mask
An area that Bahadur ignores for motion or objects. Masks are out of scope.
Detect stream
The low-resolution stream that Bahadur analyzes. Zone coordinates refer to it.
Bottom-center point
The middle of the bottom edge of an object box. Bahadur tests this point against zones.
Inertia
The number of frames that an object must stay in a zone before it counts.
Loitering time
The number of seconds that an object must stay in a zone before it counts.
Heat map
A grid that counts where objects were, over a period of time.
Dwell time
How long an object stays in one place.
VLM
Vision-language model. A model that reads an image and writes text.
SAM
Segment Anything Model. It cuts precise region masks from an image.
Grounding
Finding the image area that matches a text phrase.
Set-of-Mark
A prompt method. You draw numbered marks on regions, and the model refers to the regions by number.
MCP
Model Context Protocol. A standard method to give tools to an LLM.
Zone program
A term in this manual. A short list of geometry operations that the LLM writes.
Geometry engine
The code that runs a zone program and makes valid polygons.
Clean plate
A frame with no moving objects. You make it from the median of many frames.
IoU
Intersection over union. A score from 0 to 1 that shows how well two areas match.
Douglas–Peucker
An algorithm that removes polygon vertices but keeps the shape.
Homography
A 3 × 3 transform that maps one view of a flat scene to another view.
